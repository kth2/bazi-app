# 架构审计回应 — Prediction Engine

对外部审计报告的逐条核对。每条结论都对照了当前 `main` 分支的实际代码，
标注 **确认 / 高估 / 修正**，并补充审计未发现的问题。

审计的总体哲学 — *理论固定，推演结构化，AI 负责解释；不要让历史结果反过来改写理论* —
我完全同意，下文所有建议都在这个前提下展开。

---

## 一、总体判断

审计的核心诊断是对的，而且**核心那一条比报告写得还要严重**：

> 确定性引擎的输出在「整体命局 / 大运 / 流年 / 流月 / 流日」五个尺度上是**逐字节相同的**。

这不是推断，是代码事实。`BaziAnalysisService._analyze()`
(`lib/core/analysis/bazi_analysis_service.dart:217-218`) 在任何 scope 下都调用：

```dart
final pattern = PatternDetector.detect(chart);
final ruleMatches = RuleEngine.evaluate(chart, rules);
```

两个调用都只接受 `chart`（原局）。`decade` / `year` / `month` / `day` 从不参与。
五个尺度之间唯一的差异是：

1. prompt 里几行不同的自然语言指令（`analysis_prompt.dart:57-80`）；
2. `ChartService.luckInteractions()` 产出的一串**字符串**
   （`chart_service.dart:266-304`，形如「地支六冲: 流年 午、月支 子」）。

也就是说，从「原局有什么」到「今年会发生什么」这一整段推理，
目前 100% 由 Gemini 完成，程序只提供了一份未经解释的作用关系清单。
这正是审计第 2、6、7 条指出的问题，也是本项目当前最大的结构性缺口。

## 二、确认成立的审计条目

### ✅ 第 2 条：RuleEngine 不区分命局与岁运 — 确认，且比报告更严重

`RuleEngine._check()` (`rule_engine.dart:65-127`) 支持的 14 种条件类型全部作用于原局：
`verdict` / `seasonState` / `dayMasterElement` / `monthBranch` / `branchAt` / `stemAt` /
`hasShiShen` / `shiShenCount` / `lacksShiShen` / `hasShenSha` / `hasInteraction` /
`interactionCount` / `elementPercent` / `kongWang` / `gender`。

没有任何条件类型可以表达「流年透出官星」或「大运冲开夫妻宫」。
规则 JSON 里也没有 layer 字段可供声明。**确认，P0。**

### ✅ 第 5 条：用神输出过于粗糙 — 确认

`pattern_detector.dart:46`：

```dart
yongShen = '月令$mainGan$monthMainShiShen为用神';
```

对非禄劫格，用神=月令本气，一句话带过。没有相神、没有忌神、没有破格因素、没有救应。

但有一处审计漏掉的**积极信号**：禄劫格路径 `_luJieYongShen()`
(`pattern_detector.dart:162-176`) 已经实现了「有煞先论煞，有官先论官，无官煞再寻食伤财」
的透干取用逻辑。也就是说，**正确的取用范式在代码里已经存在了，只是只覆盖了禄劫格一条分支**。
扩展这条路径比从零建 `YongShenResolver` 便宜得多。

### ✅ 第 4 条：PatternDetector 只判「有无」不判「成败」 — 确认

`detect()` 里所有 scenario 判定都是 `countAny(...) >= 1` 形式的存在性检查
(`pattern_detector.dart:79-119`)。典型问题：

```dart
if (countStem(const {'伤官'}) >= 1 && countAny(const {'正官'}) >= 1) {
  scenarios.add('伤官见官');
}
```

`countStem` 只看天干，`countAny` 却把**全部藏干**算进去。所以一个伤官透干、
正官仅藏于日支中气的命造，会被判为「伤官见官」并把这个标签一路带到
example matching 和 prompt。审计提出的「存在 / 有力 / 可用 / 引动」四级区分是对的。**确认，P1。**

### ✅ 第 7 条：应期不应交给 LLM — 确认，且我同意这是单条性价比最高的改动

`analysis_prompt.dart:72`：

```
- 每个预测事件指出最可能的应期日（何种干支之日易触发，如逢冲之日、逢合之日），
```

程序把「哪一天」整个外包给了模型。同一个命局重问两次可以给出不同日期，
且无法解释、无法回归测试。**确认，P0。**

### ✅ 第 12 条：「流日只引动、不创事」应该硬编码 — 确认

目前这条只以自然语言出现在 prompt 里（`analysis_prompt.dart:69`），
属于建议而非约束，模型可以无视。它应该是 `EventInference` 层的一条结构性规则：
流日候选事件必须能追溯到一个已在流月/流年层成立的主题，否则不得输出。**确认，P1。**

## 三、高估或需要修正的条目

### ⚠️ 第 1 条：「flat rule scoring 是最大问题」 — 机制属实，影响被高估

审计说的 `score = weight × matchRatio` 且部分匹配可以触发，
在 `rule_engine.dart:39-44` 确实如此。但看实际规则库：

| 指标 | 数值 |
|---|---|
| 规则总数 | 81 |
| `minMatchRatio == 1.0` | **74 / 81** |
| 条件总数 | 141 |
| 标记 `required` 的条件 | **131 / 141** |
| 实际可能部分触发的规则 | **7 条** |

这 7 条是：`overall_guan_yin_xiang_sheng`、`overall_sha_yin_xiang_sheng`、
`overall_cai_guan_shuang_mei`、`career_shi_shang_sheng_cai`（均为 0.66/3 条件）、
`marriage_hong_luan_tian_xi`、`marriage_gu_chen_gua_su`（0.5/2）、
`hu_marriage_female_shao_nai_nai`（0.75/4）。

也就是说，报告中「Rule B 匹配 3/5 仍然计分」的场景在当前规则库里**不存在**。
部分匹配机制基本是惰性的。

**真正的问题在别处，而且更简单**：`score` 从来没有被任何决策消费过。它只用于

- 排序 + UI 上一个徽章（`analysis_page.dart:133-134`）；
- prompt 里 `take(8)` 拼成一行标题字符串（`analysis_prompt.dart:158`）。

没有阈值判断，没有汇总，没有下游分支。所以审计第 9 条建议的
「RuleEngine → EvidenceEngine」在工程上主要是**加 layer 标注 + 改语义**，
而不是重写打分算法 —— 比报告暗示的成本低得多。这是个好消息，
但也意味着「改打分」不该排在 P0：**该做的是让证据被消费，而不是让它算得更准。**

### ⚠️ 第 8 条：seed_rules.json 混层 — 确认，但分层方案要调整

审计说规则混合了不同推理层级，属实。当前 81 条按 `category`（整体命局/婚姻/事业/财富/学历/健康）
分组，这是**事件域**分类，不是推理层级分类，两者正交。

但审计提议的 Layer 4（岁运激活）和 Layer 5（事件象）**不应该放进 seed_rules.json**。
理由：Layer 1-3 是对静态原局的断言，可以用现有的 `RuleCondition` 表达；
Layer 4 需要时间上下文，Layer 5 需要引用 Layer 4 的输出 —— 三者的输入类型都不同，
塞进同一个 JSON schema 只会让 `RuleCondition` 膨胀成一个万能袋。

建议：**seed_rules.json 只承载 Layer 1-3**，加一个 `layer` 字段；
Layer 4 / 5 用各自独立的规则文件和条件类型。

### ⚠️ 第 11 条：案例应作为论证参考而非预测证据 — 结论对，但现状已部分达成

prompt 开头（`analysis_prompt.dart:138-139`）已经写了
「参考以下真实案例的**分析风格和逻辑**」，方向是对的。

不过有两个实际风险审计没点到：

1. `实际反馈`（真实结局，如「短短几年赚了几千万」）被原文注入 prompt
   （`analysis_prompt.dart:150`），且没有任何「不得据此外推」的约束。
   审计担心的「案例3升职所以你也升职」的通道，就是这一行。
2. 见下方补充发现 C-1，案例标签的产生方式本身不可靠。

## 四、审计未发现的问题

### 🔴 C-1：案例标签由朴素子串扫描产生，且样本只有 13 例

`AnalysisExample.fromJson()` (`analysis_example.dart:45-48`) 的打标方式是：

```dart
final tags = <String>{
  for (final kw in kPatternVocabulary)
    if (scanText.contains(kw)) kw,
};
```

在整篇分析原文上做子串匹配。后果：

- **无法处理否定**。原文若写「此造虽有伤官，然不作伤官见官论」，
  照样打上 `伤官见官` 标签。
- **无法处理层级**。文中提到「若行伤官见官之运则凶」是在讲运，不是讲原局，同样被打标。
- 语料仅 13 例，而 `kPatternVocabulary` 有 50+ 词条，标签空间远大于样本量。

更麻烦的是 `ExampleRepository.findSimilar()` 的兜底分支
(`example_repository.dart:61-64`)：命中为 0 时返回**最长的两篇**，
于是一个毫无相似结构的命局，仍然会拿到两个被标题为「案例参考」的不相关案例。
模型没有任何信号知道这两例是兜底来的。

**建议**：案例标签改为人工标注字段（JSON 里显式 `tags`），
子串扫描降级为标注辅助；兜底路径必须在 prompt 里显式标记为「无同类案例，以下仅供文风参考」。

### 🔴 C-2：变格与正格同时输出，互不排斥，且触发率约 12%

`pattern_detector.dart:125-129`：

```dart
if (support <= 20) {
  scenarios.add('从势之象（变格倾向）');
} else if (support >= 80) {
  scenarios.add('从旺之象（变格倾向）');
}
```

变格是作为**一条 scenario 追加**的，`geJu` 字段完全不变。所以输出可以是：

> 格局：偏财格；用神：月令庚偏财为用神；特殊场景：从势之象（变格倾向）

正格与变格并存，用神取月令，同时又说要顺势 —— 两套互斥的论法一起丢给模型自行调和。
`tags` 里也同时含 `偏财格` 和 `从势格`，污染 example matching。

触发频率不低。用本项目自己的打分公式（`element_strength.dart:90-146` 的 `compute()`）
对四柱在六十甲子上均匀采样 30 万次：

| 区间 | 占比 |
|---|---|
| `support >= 80`（从旺倾向） | 4.0% |
| `support <= 20`（从势倾向） | 7.9% |
| **合计标记为变格倾向** | **11.9%** |

（注：均匀采样不等于真实生日分布 —— 月支与季节相关、四柱受历法约束 ——
所以这是量级估计而非精确频率。但约每 8 个命造就有 1 个拿到自相矛盾的格局判定，
这个量级本身已经说明问题。）

同一次采样下 verdict 分布为 身弱 47.2% / 身强 34.8% / 中和 18.0%，
说明 55 / 42 这两个阈值（`element_strength.dart:133-137`）也偏向身弱一侧。
这两个数字目前是无出处的 magic number，且没有任何测试锁定其行为。

**建议**：变格判定必须**替换** `geJu` 而非追加，并从 `tags` 中移除对应的正格标签。

### 🟠 C-3：方法论自相矛盾 — prompt 说「忌以身强身弱套论」，规则库最重的三条正是身强身弱

prompt 第一句（`analysis_prompt.dart:138`）：

> 你是一位经验丰富的八字命理师，以《子平真诠》格局法论命：用神专求月令，
> 先定格局，再看成败，**忌以单纯身强身弱套论**。

而 seed_rules.json 中 `整体命局` 类目下排在最前、权重 5-6 的三条规则是
`overall_shen_qiang`（身强之命）、`overall_shen_ruo`（身弱之命）、
`overall_zhong_he`（中和之命），且每条都是**单条件必中**，
意味着任何命局必然触发其中一条，并被 `take(8)` 送进 prompt 的「规则引擎要点」。

模型同时收到「不要用身强身弱套论」和「本命身弱：喜印星生身、比劫帮身，忌财官食伤再克泄」。
在做格局法重构时这条必须一起处理，否则新的 EvidenceEngine 会继承同样的矛盾。

### 🟠 C-4：完全没有调候

代码里没有任何 寒暖燥湿 / 调候用神 的概念。`ElementStrength` 只有 旺相休囚死 的数量加权。
对于冬生水旺、夏生火炎一类命局，子平取用离不开调候，
而当前引擎只能给出「月令某某为用神」。在重构用神层时应一并纳入，
否则 `YongShenResolver` 从第一天起就是残缺的。

### 🟡 C-5：AI 结果缓存没有 schema 版本，引擎升级后旧结果不会失效

`bazi_analysis_service.dart:208-210`：

```dart
final cacheKey = 'ai_cache_${chart.baziString}_${chart.input.gender.name}_$scope';
```

key 只含命造、性别、scope。一旦引擎逻辑变更，所有历史缓存仍然命中，
用户看到的还是旧引擎产出的文本，而且无从察觉。

**这是开始重构前就该修的**，成本极低：在 key 里加一个引擎版本号常量，
每次推理层变更时递增。否则整个 P0 的效果在老用户设备上根本不会显现。

## 五、修订后的优先级

我调整了审计的排序。原报告把「改 flat scoring」放在 P0 第一位；
基于第三节的分析，那一项的实际收益低于它的实施成本，应该后移。

| 优先级 | 事项 | 相对审计的变化 |
|---|---|---|
| **P0-0** | 缓存 key 加引擎版本号（C-5） | **新增**，前置条件，改动 1 行 |
| **P0-1** | 引入时间上下文模型 + 规则声明所属 layer（审计 #2） | 保持 P0 |
| **P0-2** | `yingqi_engine.dart` — 应期移出 LLM（审计 #7） | 保持 P0 |
| **P0-3** | 变格与正格互斥（C-2） | **新增**，改动小、影响 ~12% 命局 |
| **P1-1** | PatternDetector 加 成格/破格/救应 判定（审计 #4） | 保持 P1 |
| **P1-2** | 扩展 `_luJieYongShen` 范式到全部格局 + 调候（审计 #5 + C-4） | 保持 P1，范围扩大 |
| **P1-3** | 事件层级 + 「流日不创事」硬约束（审计 #6、#12） | 保持 P1 |
| **P1-4** | 案例标注改人工 + 兜底显式标记（C-1 + 审计 #11） | **从 P2 提到 P1**：污染的是格局判定输入，不只是文风 |
| **P2-1** | RuleEngine → EvidenceEngine（加 layer 标注、改语义）（审计 #1、#9） | **从 P0/P1 降到 P2** |
| **P2-2** | 解决身强身弱与格局法的方法论矛盾（C-3） | **新增**，与 P2-1 同批 |
| **P2-3** | 推理图 + prompt 收紧（审计 #10、#13） | 保持 P2 |

### 关于「不要做」的清单

审计第 15 条列出的所有项 —— 现实反馈自动学习、自动改权重、ML 预测模型、
用户反馈训练、RAG 替代命理规则、让模型自决格局与应期 —— **我全部同意，不做。**

补充一条审计没写的：**不要把 Qimen 的引擎抽象复用过来**。
审计第 15 条已经指出两者时间结构不同，我要补充的是工程层面的理由 ——
Bazi 的 大运/流年/流月/流日 是**嵌套且各层权重不等**的（大事以流年流月为纲，
流日只引动），而 Qimen 的 局→宫→门→星→神 是**同一时刻的空间展开**。
共用一个 `ActivationEngine` 抽象一定会在权重传递上出问题。

## 六、下一步建议的实施顺序

若要动手，我建议第一批只做 **P0-0 + P0-3**（各约几十行，可独立测试、无接口变更），
先把「引擎升级能被用户看到」和「格局判定不自相矛盾」两个地基修好；
然后单独一批做 **P0-1**（时间上下文模型），因为它会改动 `RuleCondition` 的 schema，
需要同步迁移 seed_rules.json 和现有测试；**P0-2**（应期引擎）依赖 P0-1 的时间模型，排在其后。

每一批都应配回归测试。当前 `test/analysis_engine_test.dart` 用两个固定命造
（1949-10-01 与 1990-01-01）做断言，可以在此基础上扩充为格局判定的黄金用例集。

| C-4 缺调候 | ✅ | 寒暖燥湿轴（冬生喜火、夏生喜水、水旺须戊土制水），并在类注释中申明范围 |
| C-5 缓存无引擎版本 | ✅ | `kEngineVersion`（现为 3）纳入 key，旧版本与无版本条目自动清除 |

### 实施中发现、审计与本回应都未预见的问题

1. **中性喜忌被误算为凶。** 活动判定最初用 bool 表示喜忌，导致与格局无涉的十神一律落入「非喜即忌」，
   全部应期窗口清一色 `偏凶`。改为三态（喜/忌/中性）后才正常。
2. **天干相克淹没真正的冲。** bazi_core 把相克报为一个跨越多柱的节点集合，
   若按事件权重计算，每个窗口都被相克刷屏。现降为环境权重 0.15，且不得据以宣称某宫位被引动。
3. **个别十神继承整组力量。** 七杀若继承整个官杀组的力量，一个藏干七杀就能「破」掉三个透干正官的格。
   现按各自出现次数在组内按比例分配。
4. **主题门槛缺失使流日约束形同虚设。** 未设强度下限时，几乎每个十神都算「已被引动」，
   流日闸门永不生效。加入 `kThemeFloor` 后，样例月份 32 天中有 23 天确实被拦下部分主题。

## 八、案例库（实际结果回填）

用户要求「记录每个案例，日后回来回填实际结果」。这项功能与审计第 15 条
（❌ 现实反馈自动学习）**不冲突，但边界必须写死**，故在此记录设计取舍。

### 定位：复盘台账，不是训练信号

```
推演 → 存为案例 → （该运/年/月/日过去）→ 人工回填实际结果 → 人看
                                                              ↑
                                                    引擎永远读不到这一步
```

### 记录的是「可核对的断语」，不只是批文

案例快照的是**引擎的结构化断言**，而非仅 AI 的散文：

| 断语类型 | 内容 | 可核对之处 |
|---|---|---|
| 格局判定 | 正官格·破而有救 | 长期观察是否吻合 |
| 事件预测 | 事业·职务变动（吉凶参半，把握度 70%） | 应验 / 部分应验 / 未应验 / 无法判断 |
| 应期窗口 | 流月甲午（2026-06-05 ~ 07-07），强度 100% | 实际发生日是否落在窗口内 |
| 问答记录 | 用户所问 + AI 所答（原文） | 该回答后来准不准 |

一段批文无法被判定对错；「断为事业·职务变动，应期甲午月」可以。
`应验率` 只统计**可观测**的断语——`无法判断` 不计入分母，
因为「没发生」与「无从得知」是两回事。

同时记录 `engineVersion`，使任何一条回填结果都能追溯到**当时**做出该断言的引擎版本。

### 强制的单向依赖

`test/case_guardrail_test.dart` 扫描 `lib/core/analysis`、`lib/core/rules`、
`lib/core/engine`、`lib/core/models`，断言其中**没有任何文件** import 案例库。
该测试经过反向验证：故意在 `reasoning_report.dart` 加一行 import，测试即失败并指名该行。

于是「让反馈修改权重」不可能悄悄发生——必须有人先删掉这个测试。

界面上也向用户明说：**回填结果只作复盘之用，不会自动修改命理规则或权重。**

### 其他实现说明

- 案例存于**独立**的 `bazi_cases` 数据库。规则表是可丢弃的资源缓存，
  其迁移策略就是 drop + reseed；案例是手工录入的用户数据，绝不可丢，两者不能共用 schema 版本。
- 「可回填时间」= 所analyzed周期结束之时（流月看月末、流年看次年立春、大运看运末），
  而非最强应期窗口——应当在整段周期走完、每条断语都可核对时再请用户回来。
  整体命局分析没有到期日：它描述一生，永远不会「到期」。
- **问答一并记录**。用户在分析页追问的自由问答，往往是整次批算中最锋利的预测
  （「甲辰年最可能发生哪件事？1234 选哪个」会得到一个明确答案），因此原文入库，
  并与其他断语一样可判 应验/未应验，而非只留一段无从核对的聊天记录。
- 问答可能在案例存档**之后**才发生，所以重复保存时走**增量合并**：
  只补记尚未收录的问题，已回填的判定与备注一律保留。
  问题的 id 由内容做 FNV-1a 哈希得出而非 `String.hashCode`——后者不保证跨进程稳定，
  而这些 id 是要落盘的。
- 同一命局同一尺度重复保存时，先查后建，避免覆盖已回填的内容。
- **可导出为 JSON 文件**（案例库右上角「下载 JSON 文件」，或在单个案例内导出该条）。
  Web 端走 Blob + 下载链接，得到的是一个可保存、可转发的真实文件；
  非 Web 端写入磁盘并回报路径。整库导出与单条导出使用同一信封格式，
  因此二者可互换读取。剪贴板复制作为备选保留。
  导出供人离线整理成语料——引擎不读回。

### 测试说明

Widget 测试通过覆写 provider 注入内存 store，而非真实数据库：
drift 的异步连接在 `testWidgets` 的 fake-async 时区内永不完成，真实数据库会令 pump 死锁。
存储本身在 `case_journal_test.dart` 中以真实 SQLite 覆盖。
