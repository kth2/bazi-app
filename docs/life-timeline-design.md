# 人生时间线（2甲子 · 0-120岁）技术方案

> 状态：设计稿，待确认后实施。本文只定方案与数据结构，不含完整实现。

## 0. 先修正一个前提

需求里写的是 TypeScript 类型定义，但本仓库是 **Flutter / Dart**
（`pubspec.yaml` + `lib/**.dart`，无任何 TS）。下面给出的是等价的 Dart 定义。
若原意是要另起一个 Web/React 前端，那是另一件事，需先确认。

## 1. 两个实测事实（决定了架构）

以 `丙辰 壬辰 丁巳 癸卯`（起运 10.1 岁）实测：

| 项目 | 实测值 | 影响 |
|---|---|---|
| `ChartService` 返回的大运数 | **8 步（11-90 岁）** | 覆盖不到 120 岁，须扩到 12 步 |
| 每年跑完整 `ReasoningReport` | **7.5 ms** | 120 年约 900ms，扫全生会卡顿 |
| 每年只跑「引动+事件」精简路径 | **0.1 ms** | 120 年约 12ms，可即时全扫 |

**结论**：应期（`YingQiEngine`）排期占了 98% 的成本。
时间线的自动推荐走**精简路径**；应期细节等用户点开某一年时**按需计算**。

## 3. 数据结构（Dart）

### 3.1 坐标：一切以「年龄」为轴

```dart
/// 时间线的坐标系。年龄是主轴，公历年份是派生量。
class LifeSpan {
  final ChartResult chart;
  final int maxAge; // 120

  /// 起运年龄（含小数），0..qiYunAge 属小运期。
  double get qiYunAge => chart.qiYunAge;

  /// 年龄 → 公历年（虚岁口径，与 FlowYearData.age 一致）。
  int calendarYearAt(double age);

  /// 年龄 → 所在大运，未起运或超出范围返回 null。
  DecadeData? decadeAt(double age);

  /// 年龄 → 所在流年。
  FlowYearData? flowYearAt(double age);
}
```

### 3.2 事件锚点：存年龄区间，不存索引

```dart
/// 事件在时间线上的位置。
///
/// 存年龄（double）而不是大运下标或数组位置：出生时间一旦被修正、
/// 或大运步数从 8 改到 12，索引全部失效，而年龄区间不受影响，
/// 可随时重新解析到新的大运/流年。
class TimelineAnchor {
  final double startAge;
  final double endAge;   // == startAge 表示单点事件

  bool get isSpan => endAge > startAge;
}
```

### 3.3 事件本体

```dart
enum EventIntensity { low, medium, high }

/// 事件从哪来 —— 决定它能否被重算覆盖。
enum EventOrigin {
  suggested, // 引擎推荐，重算时可被替换
  userMoved, // 引擎推荐后被用户拖动过，重算时保留
  userAdded, // 用户手工添加，引擎绝不触碰
}

class LifeEvent {
  final String id;
  final String kindId;          // 见 EventCatalog
  final TimelineAnchor anchor;
  final EventIntensity intensity;
  final EventOrigin origin;

  /// 引擎给出的把握度 0..1（用户添加的为 null）。
  final double? confidence;

  /// 推荐理由链，复用 EventCandidate.basis。
  final List<String> basis;

  final String note;            // 用户备注
  final DateTime createdAt;
  final DateTime? updatedAt;
}
```

### 3.4 事件类型注册表（可配置）

```dart
enum EventSensitivity {
  normal,   // 默认显示
  guarded,  // 默认关闭，需用户主动开启
}

class EventKind {
  final String id;              // 'career.promotion'
  final String label;           // 升职
  final String domain;          // 复用 EventDomain：事业/财富/婚姻/学业发展/健康
  final String icon;            // 图标名
  final bool defaultSpan;       // 天然是区间（如财运高峰）还是单点（如结婚）
  final EventSensitivity sensitivity;
  final String? disclaimer;     // guarded 类必填
}
```

`EventCatalog` 是一张常量表 + 用户覆盖层（开关状态存本地）。

## 5. 敏感事件的处理边界

> **口径已变更（本次）**：离婚、手术、寿元、官司四类**改为默认显示**。
> 业主的决定是：**藏起一个推论本身也是一种判断，信或不信应由本人衡量**。
> 原先的「默认关闭 + 开启前须确认」整套 opt-in 流程随之取消。

保留下来的不是那道门，而是诚实：

| 保留 | 做法 |
|---|---|
| 常驻免责声明 | 不再藏在开关后面。既然标记默认显示，声明也必须默认显示——时间线图例常驻一条，点开任一敏感标记再显示该类专属的一条 |
| 措辞 | 「需留意的年份」，不是判决 |
| 逐类可关 | 设置面板从「要不要打开」变成「要不要关掉」，五类各一个开关，默认全开 |
| 密度上限 | 敏感类每步至多 1 条（`kMaxSensitivePerDecade`），全生每类至多 **2** 步（`kMaxSensitivePerKind`，普通类是 4） |

密度上限那条是量出来的：上限设 4 时，只要一张命盘触发过手术风险，它就会在
**四步大运**里各出现一次——读起来像是这个人的一种固有属性，而不是规则实际
找到的两处交汇。**把推论显示出来，和夸大它的覆盖面，是两回事。**

**寿元一项仍然不预测死亡年份。** 这不是措辞上的保守，是结构上的保证：
引擎的子类型表里根本没有任何一个词指向生命终点（`timeline_scanner_test.dart`
里有一条测试遍历全部子类型，断言不含「死/终/亡」），所以再怎么改文案也
造不出一个终点来。`寿元关注` 是 `defaultSpan` 的**区间**类型，专属声明写着
「标的是需要特别留意健康的年份区间，不是生命终点」。

## 6. 时间线组件实现思路

### 6.1 不要用 `InteractiveViewer`

`InteractiveViewer` 做的是二维矩阵变换，和 `Draggable` 抢手势，且拖放时
要把全局坐标反变换回内容坐标才能命中测试，容易出错。

改用：**一个自管的 `(pxPerYear, offset)` 状态**，平移和缩放都走同一个
`GestureDetector`。

> **P2 更正**：本节原先写的是「横向 `SingleChildScrollView` 负责平移，
> 滚动惯性免费获得」。这是错的，实现时已改。`Scrollable` 会把横向拖拽
> **连同双指拖拽一起**认领掉，捏合手势因此永远到不了 scale recognizer，
> 双指缩放直接失效。平移和缩放必须由同一个识别器处理。

```dart
// 缩放只改一个标量；平移只改另一个。两者都不经过 Scrollable。
double pxPerYear;           // 缩放级别
double offset;              // 已滚过 0 岁的像素数
double get contentWidth => pxPerYear * maxAge;
double xForAge(double age) => age * pxPerYear - offset;
double ageForX(double x)   => (x + offset) / pxPerYear;
```

好处：命中测试只是一维除法；手势没有归属之争。代价是惯性、滚动条、键盘
滚动都要自己来（P2 只做了鼠标滚轮 + 缩放按钮，惯性暂缺）。

平移与缩放合并成一句话：**手指按下时那一岁，始终留在手指下面**。
`onScaleStart` 记下这一岁，`onScaleUpdate` 用它反解 offset — 单指拖动
是 `scale == 1` 的退化情形，不需要单独一条代码路径：

```dart
// 手势开始
anchorAge = ageForX(details.localFocalPoint.dx);
// 手势更新（相对手势起点的几何，不是上一帧，否则缩放会累乘）
pxPerYear = (startPxPerYear * details.scale).clamp(minPx, maxPx);
offset    = anchorAge * pxPerYear - details.localFocalPoint.dx;
```

### 6.2 三档 LOD（缩放决定画什么）

| pxPerYear | 显示 |
|---|---|
| < 4 | 只画大运色块 + 每 10 年标注，事件聚合成簇 |
| 4-16 | 大运色块 + 每 5 年刻度，事件分开 |
| > 16 | 逐年刻度 + 干支 + 事件全展开 |

避免 120 年 × 每年多事件时一次性画上千个 widget。

### 6.3 绘制与交互分层

- `CustomPainter` 画**静态层**：大运色块、流年刻度、网格。
- 事件标记用真实 widget（`Positioned`）叠在上层 —— 因为要能点、能拖、能长按。
  数量可控（LOD 已聚合），不至于爆炸。
- `timeline_geometry.dart` 同时被 painter 和拖放逻辑引用，保证两者坐标一致。
  这是最容易出 bug 的地方：**一份映射，两处使用**。

### 6.4 拖放

- 工具栏项是 `Draggable<EventKind>`。
- 时间线整体是一个 `DragTarget<EventKind>`，`onAcceptWithDetails` 拿到全局
  坐标 → `RenderBox.globalToLocal` → `ageForX` → 按当前 LOD 吸附到
  最近的流年（放大时）或大运起点（缩小时）。
- 已存在的事件用 `LongPressDraggable` 拖动改期；区间事件两端各一个把手，
  拖把手改 `startAge`/`endAge`。

## 7. 事件与大运/流年的关联，以及一条红线

**关联方式**：事件只存年龄区间（`TimelineAnchor`），显示时才解析到
大运/流年（`LifeSpan.decadeAt` / `flowYearAt`）。所以：

- 换算逻辑集中一处，改大运步数、改起运算法都不会让存量事件错位；
- 同一事件天然能同时回答「在哪一步大运」「在哪一年」；
- 区间事件可跨大运，不需要拆成多条。

**红线**：用户拖动/新增的事件**不得回流进推理引擎**。

这与案例库那条守则是同一条：`理论固定，推演结构化，AI负责解释`。
用户把「升职」拖到某一年，不能因此改变规则权重或格局判定，否则理论就被
使用者的记忆悄悄改写了。`test/case_guardrail_test.dart` 已经在守
`core/analysis`、`core/rules`、`core/engine`、`core/models` 不得 import
案例库；`core/timeline` 已于 P2 加入同一张禁止清单。

（时间线事件要不要作为**上下文**写进 AI 提示词，是另一个问题，需单独决定——
见第 9 节待确认事项。）

## 9. 已确认的口径

| 项目 | 决定 |
|---|---|
| 120 岁口径 | **虚岁 0-120**（age 1 = 出生年，`公历年 = 出生年 + 虚岁 - 1`） |
| 事件持久化 | 挂在**命盘**（八字 + 性别），与案例库解耦 |
| 生子判据 | **男以官杀为子，女以食伤为子** |
| 重算策略 | 用户拖动过的推荐事件保留（`EventOrigin.userMoved`） |
| 时间线事件进 AI 提示词 | 暂不进，待时间线稳定后单独决定 |
| 敏感类别显示策略 | **全部默认显示**（含离婚/手术/寿元/官司），信或不信由用户判断；可逐类关闭 |
| 「破财风险」敏感级别 | `normal`，与上一条一致 |
| 寿元 | 只标**区间**，永不标终点；引擎子类型表中无任何终点词，有测试守 |
| 事件年龄边界 | 每个 `EventKind` 带 `minAge`/`maxAge`，只为挡荒谬标记；健康类无上界，与寿元无关 |

## 10. P1 实施记录（已完成）

- `_decadeCount` 8 → **12**。实测最早起运为 1 岁，第 12 步即 111-120，
  任何命盘都能覆盖到虚岁 120。
- 新增 `lib/core/timeline/life_span.dart`：年龄/公历年/大运/流年 的唯一换算入口。
  painter、命中测试、拖放三处共用，避免「画的和点的差一年」这类难查的错位。
- `endAge` 是**闭区间**（11-20 共十年），故大运在连续轴上占 `[startAge, endAge+1)`。
- 两处原本硬编码 `decades.length == 8` 的断言改为断言**覆盖到 120**，
  不再依赖一个会变的常数。
- `kEngineVersion` → 5：整体命局的应期排期原本只排 8 步大运，现在排 12 步，
  确定性输出已改变，旧缓存必须失效。

### 副作用（可见）

排盘页的大运列表与 AI 提示词的「大运列表」都会从 8 步变为 12 步。
这是必要的：时间线要画满两甲子，就不能只算到 90 岁。

## 11. P2 实施记录（已完成）

只读时间线。三个文件，职责不重叠：

| 文件 | 职责 |
|---|---|
| `features/timeline/timeline_geometry.dart` | 纯像素↔虚岁映射：`pxPerYear`/`offset`、平移、缩放、LOD、标签间隔。不含任何 Flutter 类型，可直接单测 |
| `features/timeline/timeline_painter.dart` | `CustomPainter`：小运带 + 大运色块 + 流年刻度 + 年龄轴 + 今天标线。另含 `TimelineRows`（纵向布局常量），P4 的命中测试要读同一份 |
| `features/timeline/timeline_page.dart` | 手势、选中态、详情面板、图例 |

要点与实测：

- **色块着色**：按大运天干的五行取色（`kElementColors`），阳干 alpha 0.30、
  阴干 0.16。相邻两步常是同五行（甲运接乙运），只靠颜色分不开，用深浅分。
- **刻度间隔与标签间隔是两件事**。刻度一像素就够，标签要 44 像素。
  `tickEvery` 按 LOD 给（10/5/1），`axisLabelEvery` 另按 `pxPerYear`
  从 [1,2,5,10,20] 里挑第一个够宽的。手机全览（≈3.25 px/年）落在 20 年一标。
- **今天标线**用「公历年 + 年内已过比例」定位，不是立春分界，故年初年尾可能
  差几周。仅作视觉锚点，不参与任何推演——已在代码注释里写明。
- **`LayoutBuilder` 必须放在 `Card` 里面**。放外面时 geometry 的
  `viewportWidth` 比画布实际宽度多出一个 card margin，画出来的位置和点下去的
  位置差好几岁。这个 bug 是 `timeline_ui_test.dart` 用「按 `xForAge(60.5)`
  反算坐标去点」的写法抓到的——测试里若写死像素就抓不到。
- **惯性暂缺**：自管 offset 的代价（见 6.1 的更正）。桌面/网页补了滚轮平移与
  Ctrl+滚轮缩放，另有放大/缩小/全览三个按钮兜底可访问性。

测试：`timeline_geometry_test.dart` 17 个（映射互逆、平移夹紧、缩放定点、
LOD 不跳级、标签不重叠），`timeline_ui_test.dart` 6 个（默认全览、点击选中、
小运期标注、缩放按钮、无命盘不崩）。

## 12. P3 实施记录（已完成）

自动推荐 + 标记渲染。

### 12.1 真正的难点不是算，是选

全生 120 年跑精简路径确实只要 **约 20-40 ms**（P1 的实测成立）。但输出是
**每年约 7 条候选，全生 740-960 条**。这不是时间线，是一堵墙。

更麻烦的是原始输出几乎是平的：置信度绝大多数落在 0.45-0.80，p50 ≈ 0.61。
绝对阈值要么留下几乎全部，要么一条不留。

平不是 bug。财星是不是用神，不会逐年变化，所以「财」类事件在多数年份都是
**可用的**；逐年变化的是那一年有没有真的引动它。所以扫描器换一个问法：

> **每一步大运里，最突出的是哪几件？**

这也正是大运在实务中的读法——一步运是叙事单位，问的是「这步运最该留意
哪几件事」。而且它天然限量：每步至多 `kMaxPerDecade`(3) 条，全生几十条而不是
几百条，不需要一个凭空的全局阈值。

### 12.2 三次修正（都是量出来的，不是想出来的）

| 症状 | 原因 | 修正 |
|---|---|---|
| 36 条里「职场是非×12」「压力解除×10」，只有 5 个不同类别 | 稀有度按**全生**算却按**每步**用：一个只在 12 年命中的类别，在每一步都拿稀有度加成 | 改为**密度差**：`本步命中率 − 全生命中率`。在本步和在别处一样常见的类别，就没在讲这一步 |
| 同一类别仍可能霸占所有步 | 每步独立取 top-3 | 全局贪心填槽 + `kMaxPerKind`(4)：一个类别全生最多占 4 步 |
| 「6 岁 子女之事」「7 岁 升职晋升」 | 推理引擎没有年龄概念，官杀在六岁被引动和三十六岁得分相同 | `EventKind.minAge/maxAge`。粗粒度，只为挡掉荒谬项 |

修正后：29-33 条标记，11 个不同类别，无类别超过 4 次，年龄合理
（婚恋成合 17/20 岁，升职 24/29 岁，子女之事 22 岁）。

`maxAge` 只约束**标记**能提到多老，与寿元无关：健康类**没有上界**，
全 App 没有任何一处标注生命终点。

### 12.3 敏感类别单独配额

打开 guarded 类别若与普通类别抢同一批槽位，用户打开「离婚风险」后看到的
标记总数不变、甚至挤掉了原有的——他要的是**多看到**，不是换一批。
故分两轮填槽：普通类别用 `kMaxPerDecade`，guarded 类别另有
`kMaxGuardedPerDecade`(1)。实测 29→37、33→37、31→39、31→35。

P3 的 UI 仍**不提供开关**（那是 P5），guarded 类别一律不显示；图例里明说了
哪些类别被默认隐藏，不做无声省略。

### 12.4 渲染

- **泳道在年龄空间打包**（`EventLanes`），不是像素空间。若按像素打包，缩放会
  改变泳道数，整个控件的高度会跟着手指抖动。上限 4 道，超出的挤在同一道也
  绝不丢弃——丢掉的标记既看不见也点不到。
- **颜色分事件域**（`kDomainColors`），刻意与五行色相区分：背后的大运色块就是
  五行，标记若像一块淡淡的火色带，会被读成色块的一部分。
- **吉凶不做颜色编码**。四十个标记做成红绿两色，会把参考工具变成一种情绪，
  而这个项目已经为悲观倾向返工过一次。吉凶写在详情面板的文字里。
- **强度做成分量**（alpha 0.95/0.72/0.48），不是警示。
- 点击标记出**完整推理链**（复用 `EventCandidate.basis`），并常驻一行
  「标记为规则推演的结果，非既定事实」。
- 命中测试与绘制共用 `TimelinePainter.boundsFor`，画在哪就点在哪。

### 12.5 扫描在 Provider 里，不在 build 里

`suggestedEventsProvider` 按命盘缓存。一次扫描 20-140 ms：每张命盘一次没问题，
每帧一次是灾难。

测试：`timeline_scanner_test.dart` 17 个、`event_lanes_test.dart` 7 个、
`timeline_ui_test.dart` 新增 5 个。合计 237 个全绿。

## 13. P4 / P5 实施记录

### 13.1 P4：用户编辑与持久化

存储是**第三个数据库**（`bazi_timeline`），与规则缓存、案例库都分开。不是洁癖：
`core/timeline` 被禁止 import `core/cases`，共用案例库的 schema 会打断那条
「实际结果不得流回推理」的单向依赖。

事件挂在**命盘**（八字 + 性别）上，重新输入同一组生辰即找回同一条时间线。

**合并语义是这一期的核心**。推荐事件的 id 由 (类别, 年龄) 推导而来、不是随机
生成，所以命盘不变时重新扫描会得到同一批 id，用户的改动始终落在它们原本
针对的事件上：

| 存储行 | 效果 |
|---|---|
| id 与某条推荐相同 | **替换**那条推荐（用户移动过或改过评级） |
| id 相同且 `hidden` | **移除**那条推荐 |
| id 无对应推荐 | 用户自己添加的 |

删除推荐写的是**墓碑**而不是删行——扫描器是确定性的，没有墓碑的话下次重扫
标记就回来了，删除看起来像坏了。被移动过的标记**保留引擎的推理链**：那条链
是它当初被提出的理由，改了年份之后依然值得读。

交互上**长按抓取**：普通拖拽必须留给平移轴。拖动**吸附到整虚岁**——轴在年与年
之间没有含义，42.37 岁的标记会夸大底下推理的分辨率。精确日期走编辑面板，
那是拖拽做不好的事。

### 13.2 P5：已完成的部分

**敏感类别开关 + 免责声明**（本应在 P5，提前到 P4 一起做，因为不做的话
guarded 代码路径从 UI 根本到不了）：点名的四类默认关闭，开启需先读一次免责
声明，面板里明写本应用不预测寿元、不把任何一年标为生命终点。

**新增两个事件类型**，走的是「岁运带神煞」：

| 类型 | 判据 | 说明 |
|---|---|---|
| 事业·远行出行 | 岁运地支为原局年支/日支之**驿马** | 冲动驿马主动 |
| 学业发展·贵人相助 | 岁运地支为原局日干/年干之**天乙贵人** | 贵人临 |

关键是读法：**「岁运带驿马」而不是「原局带驿马」**。第一版写成了后者，实测
结果是这两个类型在 14 张命盘上**一次都没出现**——原局带不带驿马，要么一辈子
带、要么一辈子不带，说不出是哪一年。改成岁运带之后，14 张盘里 13 张有远行、
14 张有贵人。

神煞的强度定在 `layer.authority × 0.7`，排在天干临位与地支本气之后；
结构支持度取 0.85，与宫位同档——神煞和宫位都没有通根可测，能不能落到实处
由引擎的 intensity 表达，不该在支持度上再罚一次。神煞 `stance = 0`：
驿马和贵人本身无喜忌，动得好不好看格局。

`kEngineVersion` → 6：引擎多了一类引动来源，确定性输出已变，旧缓存必须失效。
240 张命盘的吉凶平衡测试仍通过。

### 13.3 P5：**未**完成的部分（明确不伪造）

需求清单里还有五项，判据都是**组合条件**（两个以上目标同时成立），而现在的
`_EventRule` 只支持单目标匹配：

| 类型 | 需要的判据 | 为什么没做 |
|---|---|---|
| 出国留学 | 驿马 + 印星 | 需要组合规则 |
| 买房搬家 | 印星（宅）+ 财星 | 需要组合规则 |
| 名气提升 | 食伤透显 + 官星 | 需要组合规则 |
| 手术风险 | 日主受重克 + 刑冲叠加 | 需要组合规则，且是 guarded |
| 官司风险 | 官杀 + 刑 | 引擎目前把刑与冲都归为同一 effect，规则层分不出来 |

把它们硬安到近似的现有子类型上（比如拿「迁移变动」当留学）会让标记看起来

## 14. 敏感类别改为默认显示

### 14.1 决定

四类敏感事件全部默认打开。理由是业主的：藏起来本身也是一种代替用户做的判断。

原来的 opt-in 流程（默认关闭 → 弹窗确认 → 记住已阅读）整套删掉，
`TimelineSettings` 从「记住开了哪些」翻转为「记住关了哪些」——这样以后新增的
类别会以显示状态到达，而不是因为不在旧的 opt-in 名单里而悄悄消失。

### 14.2 「打开」意味着先得把它们建出来

四类里只有**离婚**是现成的（落在 感情生变 / 配偶宫动 上）。
**手术、官司、寿元三类此前根本不存在**——上一期我明确说过没做也没伪造。
所以这次的主要工作不是翻开关，是补判据。

**新增：组合规则（`_ConjunctionRule`）**。原来的 `_EventRule` 只能匹配单个引动，
而这几条最需要慎重的推论，恰恰是传统上要求**数条同时成立**的：

| 类型 | 判据 | 实现 |
|---|---|---|
| 事业·官非诉讼 | 官杀逢**刑**（为忌或中性） | 单目标 + `via: punishment` |
| 健康·手术风险 | 杀攻身为忌 **且** 日柱逢冲/刑 | 二条组合 |
| 健康·寿元关注 | 上两条 **且** 印星受冲刑 | 三条组合 |

组合规则按**最弱的一环**计分：一条链不会比它最弱的环更强，按最强环计分会让
一个响亮的引动拖出整个盘并不支持的结论。同层判定——大运的条件和流年的条件
不是同一年交汇，把它们算作一回事会让最重的推论变成最容易触发的。

**顺带修了一处**：`刑` 与 `相绝` 在 effect 层面同为 `damage`，规则层分不出来
（这正是上一期说「官司做不了」的原因）。`Activation` 增加 `via` 字段记录
来源关系，去重键把「是否为刑」纳入——只拆这一处，不是把整个 `InteractionKind`
都拆开。

## 15. 留学 / 买房搬家 / 名气：判据落地（本次）

判据由业主提供，取自传统「驿马主动、印主学业屋宅、食伤主才华、官主名位」的
成熟概念，非杜撰。以下逐条记录**实现到了什么程度**，以及**哪一部分没能表达**。

### 15.1 出国留学 → `学业发展·负笈远游`

| 给定条件 | 实现 |
|---|---|
| 岁运出现驿马 + 印星被引动 | ✅ 组合规则 |
| 印星为喜用 → 更高把握 | ✅ 拆成两条：喜用 weight 1.0，中性 weight 0.8 |
| 驿马**被冲** | ✅ 本次补回：原局驿马柱被冲刑时另发一条引动（与「岁运带驿马」是两条不同动象）。实测把命中率从 7/60 提到 13/60 |
| 印星**得地**（长生/帝旺/墓库开） | ❌ 十二长生状态不在引动模型里 |
| 华盖 / 文昌加强 | ❌ 这两个神煞未纳入事件神煞白名单 |

### 15.2 买房 → `财富·置业安家`；搬家 → `事业·迁居搬家`

| 给定条件 | 实现 |
|---|---|
| 财星有力 + 印星被引动（买房） | ✅ 「有力」取为**喜用得力**（stance 1），不是「出现」 |
| 土旺为喜（尤其辰戌丑未财库） | ⚠️ 部分：新增 `zhiWuXing` 柱级条件，岁运地支属土时另走一条更重的规则（weight 1.05）。**未**区分辰戌丑未与其他土支，也未判断土是否为喜用 |
| 驿马动 + 印星被冲/合/刑（搬家） | ✅ 组合规则 |
| 原局印弱受制、运来财星制印得宜 | ❌ 需要原局与岁运的强弱比较，引动模型没有这一层 |

两条共用「印星＝居所」这个起点，但方向相反：买房要印被**生扶**且财星到位，
搬家要印被**冲合刑**且驿马动。有一条测试断言两者在真实命盘上会分开出现，
不是同一条改了个名。

### 15.3 名气提升 → `事业·名声显扬`

| 给定条件 | 实现 |
|---|---|
| 食伤旺而有气 + 官星出现 | ✅ 「有气」取为喜用（stance 1） |
| **避免**伤官见官无制 | ✅ 食伤为忌时此条不出——这正是 stance 限定的作用 |
| 食伤生财再生官（流通） | ❌ 三步流通链没有建模，引动是单步的 |
| 伤官配印 / 食神制杀 / 伤官伤尽运来官 | ❌ 这些是**格局配置**，属于 `NatalStructure` 那一层，不是岁运引动 |

### 15.4 一处顺带的自我更正：贵人相助过度触发

上一期把「岁运带天乙贵人」直接断为贵人相助。实测下来它成了**全 App 最大的
吉性事件类**——240 盘各取一年，命中 142 次，比收入增益（86）和职位晋升（73）
加起来还接近。这不是能站住的读法：天乙贵人临是常见的修饰，不是一年的主事。

按业主给的「贵人相助＝天乙贵人 + 印星被引动」改成组合规则（渠道取印或官），
142 → 95，与收入增益、职位晋升同一量级了。

### 15.5 极性标注：一次真实的翻车与修正

三条新规则最初标成 `favourable`，240 盘的吉凶比从 **1.14 冲到 1.60**，
「偏吉占比」71% 直接把校准测试打红了（上界 67%）。

原因不是规则太松，是**极性标错**。这张表本来就有惯例：
「婚恋成合」「进修拓展」都是 `mixed`——**发生**的事标参半，只有明确的进项
（职位晋升、收入增益）才标吉。出国、置产、搬家都属前者：出国是一件大事不是
一份收益，买房同年既是资产也是负债。

改成 `mixed` 后 1.60 → 1.33，再加上 16.4 的贵人修正 → **1.23**
（吉531/凶433，偏吉127/偏凶79），回到与改动前（1.14）同一档。

这条值得单独记下来：**新增事件类型时，极性标注比判据本身更容易把整台引擎
带偏**，而且是系统性的、单张命盘上看不出来的那种。

## 16. 仍待确认

1. **「考试资格」为何从不触发**（见 15.6）。60 张盘全生扫描零命中，对一个
   命理 App 来说偏怪，判据可能过严。
